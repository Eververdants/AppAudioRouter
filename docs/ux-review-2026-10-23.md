# 体验审查 · App Audio Router 2.3.0

审查日期：2026-10-23
审查对象：`src/`（组件 18 个、store 3k 行、样式与 i18n）、`src-tauri` 的窗口配置与 `apply_route`、`docs/images`、`e2e`。
方法：通读代码路径 + 用仓库自带的 e2e 假后端实测了两条主流程与两个窗口尺寸（下文标「实测」的结论都有具体读数）。**没有在真实音频硬件上跑**：涉及声卡/蓝牙的时序结论只到代码层。

---

## 结论速览

骨架是好的：零 IPC 首帧、窗口首帧后才揭幕、两个常驻循环都有卸载闸门、Esc 的层叠纪律与焦点归还、就地二次确认、路由可撤销、错误按动作批处理成一张卡——这些都比同类工具做得细。

问题集中在**「计划 / 事实」这套模型的两个洞**：

1. **计划可以等于事实，而且仍然可以提交。** 选中一个未路由的程序，hub 立刻变成「点按生效」；按下去声音一点没变，却把程序钉死在当前默认设备上（实测 `apply_route(pid, ["speakers"])`）。这是"点了没反应，但留下了副作用"，最伤信任。
2. **「改到另一台设备」的入口，比「加一台」弱一个数量级。** 最显眼的 ＋ 只会追加副本，于是"让 Spotify 只在耳机里响"这个最高频的意图，按最自然的操作会变成两台同时响（实测 `["speakers","tv"]`）。

再往下是三类系统性问题：**错误态被当成空态**（读失败说成"没有程序在放音"）、**亮色主题有 5 组配色不到 AA**（含向导主按钮）、**窗口只要一缩就裁掉看板且没有滚动条能救回来**（最小宽 720 时左栏被滚出 38px，`body.scrollWidth` 仍是 720）。

## 一、交互流程

### U1 · P0 · 计划等于事实时可提交，副作用是钉死设备

**用户看到的**：在左栏点任意一个还在默认设备上播放的程序 → 中间卡片立刻浮出「Click to apply / 点按生效」胶囊，`aria-label` 是 *"Play music.exe through Speakers instead"*（实测；e2e 跑在 en 语言下）。按下后：声音没有变化，标题栏计数 +1，右下角弹出「music.exe → Speakers · 撤销」，活动记录写「已将 music.exe 路由到 Speakers」。

**实际发生的事**：`apply_route` 无条件写 per-app 端点（`commands.rs:236`）并登记 `pins.mark`（`:242`）。也就是说，这一次"什么都没改"的点击，让该程序从此不再跟随 Windows 的默认设备——而应用自己的启动提示还在为旧版本留下的这种固定端点向用户道歉（`startup.welcomeBody`）。

**根因**：`alreadyApplied` 只拿计划和 `routedPids` 比（`lib/stage.ts:34-53`）；未路由程序的路由表是空的，于是"计划 = 系统默认设备"永远被判定为"未生效"。可 `selectionTargets` 又把系统默认设备预填进计划（`routerStore.ts:464-471`）。board-ui.md「计划与事实」一节写的是"刚选中时屏幕上出现的是现实"——那么按它自己的原则，现实不该再被问一次"要不要生效"。

**建议**（前端 10 行左右）：

```ts
// lib/stage.ts —— 判定的基准是「此刻实际在哪」，不是「有没有路由」
export function answeredAsShown(
  staged: string[],
  pids: number[],
  routed: Record<number, string[] | undefined>,
  fallback: string | null, // 未路由时的系统默认设备
): boolean {
  return pids.every((pid) => {
    const ids = routed[pid] ?? (fallback === null ? undefined : [fallback]);
    return ids !== undefined && ids.length === staged.length && ids.every((id, i) => id === staged[i]);
  });
}
```

计划 == 现实 → hub 退回普通面板（现在的"已生效"形态），「点按生效」不再出现。若确实需要"把这个程序钉死在当前设备"，做成一条显式动作（例如调音条里的"固定在此设备"），别藏在主按钮里。

> 这条和 U2 是同一条主线的两端：**模型允许"无变化"存在，却把"变化"藏在次级入口。** 先修 U1，再修 U2。

### U2 · P1 · 「改到另一台」藏在最弱的控件里，＋ 只追加副本

用户意图最常是"这个程序改到耳机/电视上"。看板上最显眼的可点物是复制面板标题行的虚线 ＋（`NodeStage.tsx:944-960`），它的 `title` 是"再输出到一台设备，或送进另一个程序的输入"——**"再"字承担了全部后果**，而它在 10px 的 tooltip 里。

实测（未路由程序）：

```
点 ＋ → TV        方案行 = ["speakers","tv"]
按 hub             apply_route deviceIds = ["speakers","tv"]   // 两台同时响
```

正确的"换设备"路径是主设备行的**名字**（打开「更改主设备」选择器 → `setPrimaryDevice`，整条方案被替换）。但这个入口：没有图标、没有箭头、没有下划线，hover 时才把下面的"主输出"三个字换成带虚线下划线的"更改主设备"（`NodeStage.tsx:1443-1468`）。

**建议**（三条任选，建议 ①+②）：

1. ＋ 的 `title` / 菜单段标题写明后果：菜单分两段——**「改到这台播放」**（`setPrimaryDevice`，默认段）与**「同时输出到这台（复制）」**（`appendDeviceTarget`）。用户脑子里只有一个目标设备时，第一段就是他要的。
2. 主设备名字右侧加一个常显的 `⌄`（或一枚 12px 的"改到…"胶囊），与 ＋ 同级重量——现在它只有"文字"的重量。
3. 追加副本成功后，让 hub 的胶囊带数量：「点按生效 · 2 台设备」，把多出来的那一路摆到按下去之前。

### U3 · P1 · 不可见的 ✕ 仍然可以点

`ProgramRail.tsx:478-506`：停止路由的 ✕ 外层是 `opacity-0 … group-hover/row:opacity-100`，**没有 `pointer-events-none`，也没有 `hidden`**。它一直占着位置、一直可命中。鼠标用户靠 hover 先看见它，问题不大；触屏/笔用户看到的是"这一行右边没有东西"，点下去却停掉了一条路由（第一下 armed，第二下执行，但 armed 态同样只在 hover 时才可见）。

同类：MiniToggle 常态 `opacity-30`（`ProgramRail.tsx:540`）——一个把程序并进批量操作的关键控件，默认几乎看不见。

**建议**：不可见时 `pointer-events-none`（arm 之后才接管）；`@media (hover: none)` 下这些控件常显（`opacity-100`）。全仓库目前**没有任何 `hover: none` 查询**，这是触屏适配的第一块砖。

---

### U4 · P1 · 状态词是按钮

`NodeStage.tsx:1475-1491`：副本行的"副本"二字是一个 `<button>`，hover 时文字换成"设为主输出"，点击执行 `promoteDevice`。设计上想解决"状态词也是入口"的密度问题，但代价是：

- 触屏没有 hover，**点一个状态词会重排整条路由**（主设备换人），且 `promoteDevice` 不写日志、不弹 toast（`routerStore.ts:1280-1293`），用户没有任何确认。
- 键盘用户 Tab 上去时它才变成动作词——焦点到达前，它看起来仍然是标签。

**建议**：角色词回到纯标签；旁边常驻一枚 12px 的 ⇄ 按钮承担 promote（`aria-label` 用"设为主输出"），hover 时把 ⇄ 变成 accent。密度几乎不变，但"标签"和"动作"分开了。

---

### U5 · P1 · 读取失败被说成空态

`refreshSessions` 失败时：只在**列表还没建立**时写日志，然后 `finally` 里 `set({ sessionsLoaded: true })`（`routerStore.ts:1150-1163`）。左栏据此显示：

> 未检测到正在播放音频的程序
> 请先让程序播放声音，再刷新

——这是一个关于机器的断言，而事实是"我们没读到"。同理：设备枚举失败后，延迟设置页说「暂无音频设备」（`SettingsPage.tsx:754-757`），看板主设备面板说「还没有输出设备」。

**建议**：store 增 `sessionsError: string | null` / `devicesError: string | null`（`finally` 里按成功/失败分别写），空态三态化：

```
读取中 → Spinner + "正在读取…"
失败   → "没能读取程序列表" + 原始错误（小字）+ [重试]（复用 rail.refresh）
确实空 → 现在的文案
```

左栏已经为"读取中"和"确实空"做了区分（`ProgramRail.tsx:73, 247-279`），把这条规则推到"失败"和设备列表就行。

## 二、错误与反馈

### U6 · P1 · 错误卡：8 秒、无动作、露后端原文

- `TOAST_DISMISS_MS = 8000`（`Toast.tsx:9`）。
- 文案普遍是「路由失败：{{error}}」，而 `error` 是 `String(e)`，来自 Rust 的英文串（「a route needs a process」「device 2 of this route is not usable: …」）甚至 HRESULT。中文界面里夹英文错误，用户既读不懂也不知道下一步。
- 卡片上没有按钮，唯一的出口是等 8 秒或按 Esc；要复读只能去第三页。
- 半数失败**不可重试**却仍按瞬态处理：`duplicationFailed`（引擎起不来）、`mirrorFailed`（某台设备没声音）——这些是持续状态，用户很可能在别处做事，回来时通知已经消失，只留下"怎么没声音"。

**建议**：

1. 给每个 `raiseError` 加一个可选的 `action`：`{ label, run }` 或 `{ label, href: 'activity' }`。能重试的（route / stop / refresh）给"重试"，其余给"查看记录"。
2. 主句说人话，码放第二行（10.5px muted）或 `title`：`log.routeFailed` 保留「没能把这个程序改到 X」，`{{error}}` 只进小字与日志。
3. 持续性失败（mirror / duplication）不要用 toast：把状态写进对应行/卡片（设备行标红 + `title` 给原因），并在「活动记录」标签上点一个未读圆点，直到用户打开。

## 三、视觉与可读性

### U7 · P1 · 亮色主题 5 组配色不到 AA

实测对比度（WCAG 2.1，普通字号需 4.5:1）：

| 用途 | 前景 / 背景 | 实测 | 结论 |
|---|---|---|---|
| 强调色文字（撤销按钮、设置选中项、`+n`） | `#0891b2` / `#ffffff` | **3.68** | 不达标 |
| 白字压在强调色上（向导「开始使用」、hub「点按生效」10px） | `#ffffff` / `#0891b2` | **3.68** | 不达标 |
| 错误文字（日志错误行、armed 确认按钮） | `#ef4444` / `#ffffff` | **3.76** | 不达标 |
| 次级文字在凹陷面板（看板井底、面板标题） | `#71717a` / `#f2f3f5` | **4.35** | 不达标 |
| 次级文字在窗口底 | `#71717a` / `#eef0f3` | **4.23** | 不达标 |
| 深色主题同项 | — | 6.6–10.1 | 通过 |

**建议**（亮色，深色不动）：

- 可读的强调色用 `#0e7490`（白底 5.36，白字压上也 5.36）——它已经存在于色板里（`--accent-hover`）。`#0891b2` 只留给 1px 线、图形、`Ring`（非文字只需 3:1）。
- 错误文字用 `#dc2626`（4.83），`#ef4444` 留给圆点与描边。
- 凹陷面板上的次级文字改 `#5b5b63`（6.06 / 5.89），或在这些表面上直接用 `--text-secondary`。
- 这条要落成 token 层面的规则（`--accent-text` / `--accent-mark`），否则下一个组件还会拿 `--accent` 写字。

### U8 · P1 · 窗口尺寸是刚性的，一缩就裁

实测（Chromium，页面即应用）：

```
900×680（默认）  well 664×600，看板 640×600   → 左右各 12px 余量
720×520（最小）  well 640×440（被内容撑开），aside.left = -38，body.scrollWidth = 720
```

第二行说明：根容器被**滚掉了 38px**（浏览器为了露出焦点元素自己滚的），左栏被推出窗口；同时 `body.scrollWidth` 仍是 720，也就是说**没有任何滚动条能把它滚回来**。截图里左栏只剩"…ers +1"和"Refresh"一条边，看板右列也压在窗口外。

设计上 `BOARD_W = 640` 是硬编码的（`stage.ts:64`），左栏 236，合计 878——而产品默认窗口只有 900，最小窗口允许 720。**默认尺寸只比布局最小值多 23px**，用户拖一下窗口就进破损区。

**建议**（短期立刻、中期再谈）：

1. `minWidth: 900`（878 + 一点余量），默认 `980×720`。这一条就消掉破损区，代价是"窗口不能更窄"。
2. 中期：看板加缩放层——`well.clientWidth < 664` 时给 640 板套 `transform: scale(w/664)`（几何仍只由 `stage.ts` 一套数决定，`useElementHeight` 照旧报高度）。缩放会带来命中区同步变小的副作用，所以要配 `min 0.85` 的钳位。
3. 或 < 900 时把左栏折成 56px 的图标栏（`Ring` + 图标，名字进 tooltip），把 180px 还给看板。
4. **e2e 默认 viewport 是 1280×860**（`playwright.config.ts:28`），比产品窗口大得多——这解释了为什么这类问题测试里看不见。至少加一条 900×680 的用例，断言 `board.getBoundingClientRect().right <= window.innerWidth`。

### U10 · P2 · 字号 13 档，42 处 < 11px

实测分布：

```
11px ×65   12px ×23   10px ×18   12.5px ×12   9.5px ×10   11.5px ×7
10.5px ×7  9px ×5    13px ×4    8px ×2       19px ×2     17px ×1   15px ×1
```

< 11px 共 42 处。而它们承载的恰恰是要读的东西：延迟读数 `+140 ms`、份额 `70%`、PID、角色词「主输出 / 副本」、hub 状态行。100% 缩放的 1080p 屏上 9.5px ≈ 7pt。

**建议**：定 4 档并写进 `tailwind.config.ts` 的 `fontSize`：`xs=11 / sm=12 / base=13 / lg=17`。9.5/10/10.5 一律收到 11（mono 数字最小 11）；`8px` 的字母瓦片是图形，可以留。这条不是审美问题——它直接决定"副本 +140 ms"能不能一眼读到。

### U11 / U12 · P2 · 命中区与焦点

- 命中区：✕ `h-4 w-4`（16）、MiniToggle `h-5 w-5`（20）、编号角标 `20×18`、调音条 ± `h-4 w-4`（16）。WCAG 2.5.8（AA）要求 24×24。
- 焦点：编号角标按钮只有 `hover:`（`NodeStage.tsx:1405`），设备名按钮只有 `focus-visible:text-accent`（`:1434`），`FeedRow` 的 ✕ 只有边框变色（`:1714`）。一个纯键盘用户 Tab 到角标时，屏幕上没有任何变化。

**建议**：命中区用伪元素撑（`before:absolute before:-inset-1.5`），视觉大小不动；`.no` 加 `focus-visible:ring-2 focus-visible:ring-accent/60`，全站统一"2px ring + 2px offset"。

### U13 · P2 · 三个数值控件，三套交互

- 调音条（`StripRow`，`NodeStage.tsx:1766-1826`）：只有 −/+，份额 5% 一步 → 从 100 到 0 要 **20 次点击**；延迟按 step（默认 10ms）→ 0 到 180 要 **18 次**。
- 设置页（`DelayStepper`）：−/+ **外加可直接键入**。
- 电平环（`ScrubReadout`）：拖拽 / 滚轮 / 方向键 / 点击键入，提交走 300ms 静默合并。

同一类数字（毫秒、百分比）在三个地方三种手感。**建议**：`StripRow` 直接换成 `ScrubReadout`（组件已在、有测试、`SourceLevelDial` 就是它），一次消掉 20 连击与命中区两个问题。

### U14 · P2 · Toast 和胶囊、调音条抢同一个锚点

```
Toast        fixed inset-x-0 bottom-0   p-4  z-40   → 占 16–50px
RoutedCapsule absolute bottom-[56px]    z-30       → 占 56–88px
调音条        贴底（border-t, py-2.5）              → 占 0–41px
```

一张 toast 就压住调音条的上半（延迟/份额那一行）；两张（错误 + 撤销）时上面那张正好压在「已路由 n」胶囊上。实测截图里，刚路由完的那 8 秒，底部的三条信息是叠在一起的。

**建议**：toast 层让位：调音条开着时 `bottom: 64px`，否则 `bottom: 96px`；或把 toast 移到右上（Windows 原生通知也在右下，但这里右下已被两个常驻控件占满）。至少要保证"临时层永远不覆盖常驻控件"。

### U15 · P2 · 单设备路由没有任何音量入口

`badgeIsButton = drawn.length > 1`（`NodeStage.tsx:285`），board-ui.md 第 122–123 行明确这是刻意的：单设备没有引擎，主输出音量没有可落的路径。

技术上成立，但用户目标是"把这个程序调小"——这在单设备时是**最常见**的一次调音，而应用里对它零入口（连一句"去 Windows 音量合成器"都没有）。

**建议**（承认规则，补一条出路）：单设备时在主设备行下方加一行 10.5px 的说明 + 一个可点的词——「音量在 Windows 音量合成器里调」→ `sndvol.exe`，或 `ms-settings:apps-volume`。想更彻底，则让后端对无引擎的会话单独写 session volume，那时 `drawn.length >= 1` 就能开调音条。

### U16 · P3 · 左栏次级行：冗余挤掉了有用信息

截图里是 `Music.exe · PID 4021…`——exe 和显示名只差一个 `.exe`，却占满了整行，把 PID 挤到截断（`ProgramRail.tsx:359-362` 只做小写全等比较）。而 PID 恰恰是排查"两个同名程序"时唯一有用的东西。

**建议**：显示名去掉 `.exe` 后与 exe 相同 → 不显示 exe；PID 放到行首或收进 `title`；次级行最多两段，第三段一律进 tooltip。

### U17 · P3 · Inter 没打包，字体栈还有两份

`index.html:66-72` 的 critical CSS 里没有 `'Microsoft YaHei UI'`，`index.css:168-175` 里有；`Inter` 在仓库里没有 woff2（CSP `font-src 'self' data:` 是允许自带的）。所以绝大多数 Windows 机器实际渲染的是 Segoe UI——而看板的名字槽宽 106px、`BOARD_W 640`、`clampHubName` 的 12.5/7px 估算，都是按 Inter 的度量定的。

另外：首帧的字体栈和 CSS 加载后的不一样，中文用户开机时会看到一次字体跳变。

**建议**：二选一——(a) self-host Inter（latin 子集 woff2，~30KB，`font-display: swap`）；(b) 把 `Inter` 从栈里删掉，以 Segoe UI 为设计基准重校那几个字面量。无论哪条，两份字体栈要合并（critical CSS 由构建注入同一份）。

`docs/images/*.png` 是 2026-10-11 的，标签栏只有 `Routing / Activity`；当前是三个（路由 / 现状 / 活动记录，`BriefingPage.tsx` 于 10-21 加入）。AGENTS.md 里"改 UI 后重拍并核对图注"这条，这次没跟上。

## 四、加载与响应

整体做得比多数 Tauri 应用好：首帧零 IPC、`afterFirstPaint` 之后再枚举、窗口首帧后才揭幕、5s 看门狗防水。真正的问题只有两处。

### U9 · P2 · 首次运行闪一帧空看板

`startupNotice` 初值 `null`（`routerStore.ts:964`），`loadStartupNotice` 排在 `afterFirstPaint` 里（`App.tsx:165`），而窗口在首帧提交后就揭幕。于是新用户第一次打开：先看到空左栏 + 「请先在左侧选择一个程序」+ 设置齿轮，100–300ms 后整页换成向导，齿轮消失（`hideSettings`）。

**建议**：`startupNoticeLoaded` 标志；未就绪时工作区不渲染（或渲染同一块骨架）。更省事的做法：`getStartupNotice` 是 Rust 侧的同步读盘，把它从 `afterFirstPaint` 移到揭幕之前（它不碰 Core Audio，不吃首帧预算）。

### U19 · P3 · 「刷新」没有进行中状态

`refreshSessions` 有 in-flight 门（`routerStore.ts:1054-1057`），但界面不知道。蓝牙重连时点"刷新"，几秒钟毫无反应，用户会再点（请求被排队）再点。

**建议**：store 暴露 `sessionsRefreshing`，左栏按钮 200ms 后转成 spinner 或"刷新中…"并禁用。

### 写进"性能"但其实是可读性的

向导的 `BlurText` 把整句拆成逐字的 `filter: blur()` 动画（`StartupWizard.tsx:34-62`）。一句话 40–60 个字符 = 40–60 个元素同时做滤镜动画，且**每个字都要等自己的延迟到才可读**——第一印象是"这一屏要等它演完"。首屏本来就该是最快的一屏。

**建议**：标题保留逐字（短，有仪式感），正文改成整段 200ms 淡入（或只做行级 stagger）。真要保留逐字，把 `filter` 换成 `opacity + translateY`，避免同时驱动 60 个滤镜层。

## 五、移动端 / 触屏 / 高 DPI

**这条需求在本项目里不成立**：它是 Windows 桌面应用（Tauri，无 Web 版、无移动端构建）。强行做响应式断点没有收益。真正对应"移动端适配"的三件事是：

| 场景 | 现状 | 对应条目 |
|---|---|---|
| **触屏 / 笔**（Windows 平板、触屏本） | 全仓库 0 处 `@media (hover: none)`；停止入口与 MiniToggle 只在 hover 时可见却仍可命中；「副本」一词点下去会改主输出 | U3、U4、U11 |
| **高 DPI 缩放 125–200%** | 字号最小 8–10px，125% 下相当于 12.5px 设备像素，视觉上仍偏小；看板固定 640 不随缩放变化 | U10、U8 |
| **窄窗 / 分屏 / 小屏笔记本** | 最小宽 720 直接进破损区；默认 900 只有 23px 余量 | U8 |

另外两条只跟触屏有关、值得单独做：

1. **悬停语义要显式化**：`@media (hover: none) { .hover-only { opacity: 1; pointer-events: auto } }`，一条规则覆盖全站（现在这些类散在 6 个组件里，建议抽成 `.hover-reveal`）。
2. **拖动/滚轮不是触屏手势**：`ScrubReadout` 的拖拽在触屏上会和页面滚动打架（`touch-action` 未设置）。若要认真支持平板，给它加 `touch-action: none` 并换成"按下 → 竖向拖"的保守手势。
